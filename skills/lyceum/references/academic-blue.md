# 学术蓝白 · 内容与图示规范（默认）

适用于组会、开题、答辩、进展和论文分享。先按场景组织论证，再用本规范构图。
用户指定的院校模板、配色和页面密度优先；旧主题仍可显式选择。

## 视觉方向

白底、深蓝标题、黑色正文；通过细描边、色带、对齐和箭头建立层次。
参考图的价值在于“研究内容与结构图一起呈现”，不是其中的占位文字、装饰照片或红色大色块。
不再把大留白、悬浮卡片、巨大数字当作学术感的必要条件。

```text
BG / SURFACE  FFFFFF
INK           174A88   # 标题、主流程、表头
P_MID         096CA8   # 方法模块
P_SOFT        EAF3FB   # 轻背景、表格间隔
TEXT          202A35
MUTED         526477   # 图注也必须清晰
LINE          B8CADB
TEAL          008579   # 数据准备
GOLD          B87B00   # 验证 / 待执行
ACCENT        B73535   # 问题 / 风险
CHART_RAMP    [174A88, 096CA8, 648DAE, B6CADC]
```

TEAL / P_MID / GOLD 可以在同一技术路线页编码不同阶段，必须同时有阶段名称，
不可只靠颜色区别。ACCENT 可以复用在同一风险链条的标记和结论中。
普通页面不加阴影；小圆角只用于确有分组意义的模块。封面也默认白底。

## 网格与文字

- 16:9，13.333 × 7.5 英寸，四周边距 0.5 英寸。
- 页眉：章节标识 y=0.26，12–14pt；标题 y=0.64，28–30pt 粗体；短蓝线 y=1.30。
- 内容带 y=1.52–6.82，页脚 y=7.08。标题最多两行，需两行时整体下移内容带。
- 正文 18–20pt；图内标签、表格 14–16pt；图注、来源、页脚至少 12pt。
- 中文微软雅黑，英文与数字 Segoe UI；两者分 run，表格单元格也按此处理。
- 上方可放 1–2 行概括，主体放图与解释，下方放一句判断或阶段说明。
- 不通过自动缩小字体塞内容；优先压缩空容器、删重复、改列宽、合并碎页。

## 信息密度

一个页面完成一个**研究任务**，可以包含相互支持的子结论。不要仅因为标题中有
“与”“和”就拆页。例如实验设置、结果图、局限与结论应该放在一起，便于核对。

常规内容页可有 3–5 个有用信息单元：问题、机制、证据、解读、下一步。
目标是读者看一页就能理解研究逻辑，而不是满足字数。约 120–260 个汉字加图表
是组会/开题的一种起点；会议口头报告可更少，备查页可更多。没有足够事实时，
合并页面或注明尚未完成，绝不为了填满页面补造数据。

正文行数按区域分配，不设“全页不超过八行”的硬上限。避免一行观点占一个大卡片。
图表与说明通常占内容带约 75%–90%，保留模块间隔；不要把背景色块算成信息。

## 三种优先构图

### A · 横向技术路线（参考图一）

全宽五段：研究问题 → 数据准备 → 模型/方法 → 验证 → 输出。
中间三段可各用 TEAL、P_MID、GOLD 的标题条与浅色底，首尾用蓝色描边。
每段包含：具体输入/操作、可编辑小示意、输出名称；箭头表达真实的数据流。
下方三列对齐说明数据范围、关键机制、验证指标/基线。若无物理约束等机制，
不可从参考图照搬。模型框不能只写“模型构建”四字。

可用宽度 12.33，五个模块约 2.20，间隔约 0.33；模块 y≈2.1–5.2，
底部解释 y≈5.5–6.8。首尾有复杂问题时可以加宽并压缩中段，不能压小标签。

### B · 左流程、右论证（参考图二）

左侧约 25%：科学问题 / 研究方法 / 预期成果，竖向箭头连接。
右侧约 75%：每行分别解释“缺口及边界 / 机制及变量 / 验证及交付物”，
每行 2–3 行有效正文，可嵌入迷你架构、参数关系或验收表。
用细虚线分隔对齐的行；每行的左标签与右正文必须一一对应。

### C · 背景证据 → 科学问题（参考图三）

左侧约 55%：标题条、2–3 行具体背景、真实案例/数据图/任务示意。
中间箭头表达从观察到问题的推导。
右侧约 37%：问题名称、范围、现有方案缺口、研究目标；可用浅红底和红色边框。
“提出科学问题”不是正文。不能用与研究无关的图库照片或放大镜填空。

## 按页面任务选图

| 页面任务 | 主要 figure | 同页说明 |
|---|---|---|
| 背景/动机 | 数据证据、任务场景或真实案例 | 矛盾 → 可验证问题 |
| 研究内容 | 问题—方法—成果对应图 | 每项做什么、怎么验证 |
| 技术路线 | 输入—处理—验证—输出流程 | 数据范围、关键机制、阶段产物 |
| 方法细节 | 模块图、数据流、关键公式 | 设计动机、假设、训练/推理区别 |
| 实验结果 | 原生曲线/柱状图 + 必要的小表 | 设置、基线、数值解读、局限 |
| 问题分析 | 错误案例/曲线 + 排查链 | 观察、已查项、未验证假设、下一步 |
| 计划 | 甘特图/依赖图 + 验收表 | 时间、负责人、产物、风险 |

大多数内容页应有实质图示；封面、目录、文献、纯讨论页可例外。
figure 不是“图标数量”：一个有数据流和说明的流程图比五个无关系图标更有用。
尽量使用源论文 figure、用户实验或可编辑重绘；缺少结果时画方法/实验设计图，
并在页内明确标“设计示意”，不要画看似真实的实验曲线。

## 来源、编辑性与检查

- 图表使用原生图表及内嵌数据；示意图使用原生形状、连线和标签。
- 外部 figure 保留来源、图号与必要的轴/图例，不裁掉反证；重绘标“改绘自”。
- 数据必须在同页 notes 存底；示例数据在每页页脚及 notes 明确标“虚构演示数据”。
- 来源不足时不写显著性、不杜撰 p 值、重复次数、论文或不存在的附录。
- 先检查几何/字体/占位符，再检查内容密度及 figure，最后逐页渲染目检。
- `qa_check.py --academic` 给出图表/原生流程候选数量、字量与稀疏提示；
  它不判断科研真实性或流程含义，不替代视觉和内容审查。

可运行实现见 `examples/group-meeting-demo/build_demo.js`，覆盖上述三种构图、
方法架构、结果图表、排查流程与计划。入口脚本从仓库根目录运行。
构建后用 `scripts/normalize_pptx.py` 处理 PptxGenJS 4.0.1 的重复段落属性问题，
示例脚本已自动执行。Windows 可用 `scripts/render_powerpoint.ps1` 验证原生打开和逐页导图。
